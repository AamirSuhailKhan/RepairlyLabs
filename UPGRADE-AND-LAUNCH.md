# RepairlyLabs — audited operations and UPI QR upgrade

This is the full source tree, based on `RepairlyLabs-main (2).zip`, not a manifest or a separate mockup. The original storefront styling and request/order functionality are retained. It requires Node.js 22.13+ and a single persistent server instance. This is a tested upgrade, not a certification that every proposed feature is complete.

## Upgrade your actual project (your coding agent can do these steps)

1. Stop the running application. Identify the actual project path, `.env`, and `DATA_DIR`. Back up using a consistent SQLite backup (`npm run backup` with the original configuration), keep a separate copy of the existing source and verify the backup. Never overwrite or delete live customer data.
2. Merge this full source tree into the actual project directory, preserving `.env` and the entire live `data/` directory (or externally configured DATA_DIR). The ZIP contains no live database, credentials or merchant QR. Additive migrations execute on startup. Existing account usernames, password hashes, repair records, payment rows, reference registry and sessions are preserved; existing team accounts default to technician permissions until the owner assigns the appropriate role.
3. Use the actual project configuration; start with `npm start` (the agent or server operator runs this). Run `npm test` and `npm run audit` using isolated test databases. No daily terminal commands are needed once the application is running.
4. Open `/admin`. Sign in with the existing owner credentials. If unavailable, ask the trusted agent to run `node scripts/agent-owner-recovery.mjs` from the actual project and open its private one-time URL. Do not publish that URL. It checks the running server and database. No CMD/VBS launcher is required. Passwords: 8–150 characters; use a long unique password. Then Security > Offline recovery codes: generate and securely save five single-use codes for browser-based recovery without launcher access. Email login is not verified email recovery; an email alone cannot reset an owner account.
5. In Security, assign your staff manager, technician or accountant permissions. Technicians only see jobs whose technician account username matches their account. Owner/manager can assign a technician using Repair Desk. Accountant may see repair and payment details; only owner can change merchant destination or export customer data. Existing staff may need their permissions updated after upgrade.
6. Open Repair Desk at `/repair-center/?admin=1` (link in main admin). Choose UPI QR settings. Upload your real merchant PNG/JPEG QR (max 500 KB), enter merchant display name and optionally UPI ID, enable it, and re-enter the current owner password. Scan the actual image and verify the intended merchant recipient before enabling. An upload is checked for file format/size, not whether its QR content is valid or its bank recipient is yours. Do not upload a sample QR.
7. Submit a test repair, inspect and quote, approve via the customer portal using the private code, record any required advance, complete quality checks and work, submit a test payment reference, verify actual credit independently, and record the decision. The application never treats an uploaded screenshot or UTR as proof of bank receipt. Do not use fabricated credits in live records.
8. Fill real business details, pricing, inventory, hours, tax/warranty policies, and consent/privacy notices. Configure production HTTPS and PUBLIC_ORIGIN, persistent disk, secrets, offsite backups, monitoring and actual notification providers. Review local browser workflows before public launch.

## What's implemented

- Permanent unique repair/parts reference registry retained; booking duplicate protection and high-entropy request-key replay for same-form retries, including parts checkout. No plaintext customer access codes stored on server; recovery tokens are hashed. A different new form submission is not guaranteed to be a duplicate.
- Actual date validation (invalid calendar dates rejected), additional email/PIN/time preference/WhatsApp fields, intake display and IST timestamps. Slots are requested preferences, not a capacity scheduler or geographic serviceability check.
- Atomic bulk model imports, 404 missing contacts, central .env and DATA_DIR resolution for server/setup/backup, stale payment terms corrected when unchanged from original defaults.
- Main admin repair list now links to Repair Desk; compatibility API permits only initial pending/confirmed status and indicative quote updates, prevents completion/delivery bypass. Existing legacy records are preserved and may require manual reconciliation.
- Owner, manager, assigned technician and accountant permission boundaries; eight-character minimum; hashed single-use browser recovery codes after authenticated generation. Existing private operator recovery alternative remains.
- Static business QR upload, server-owned amount checks, payment claim review, optional private PNG/JPEG screenshot (stored inside SQLite, not public assets), unique UTR for pending/verified claims, rejection, event log, owner password verification on destination changes, payment search dashboard and customer payment history. One open attempt per repair; static QR does not technically prevent someone making a second bank transfer outside the app. Verify actual amount, recipient and UTR from merchant bank records before approval.
- Existing Razorpay checkout retained. Explicit 400/401/403/422 create-order rejection records a failed attempt; timeout, 5xx, malformed or ambiguous response records reconciliation_required. Do not blindly retry unknown outcomes. Owner can release unresolved creation only after provider confirms no order/credit, with current password and evidence. Existing open gateway order remains locked until safely reconciled; capture signature/amount checks retained. Mock provider tests do not establish live provider behavior.
- Manual cash, partial advance/final payment, actual offline pre-delivery refund recording (does not send money), net ledger balances, revised quotes after settled advance (renewed customer approval, no negative balance). Stable repair statement reference, printable statement, not a GST tax invoice.
- Technician assignment, required pass/fail/not-applicable quality checks, SKU-linked stock deduction on completion (optional exact verified active SKU, no deduction for unlinked line). Inventory transaction prevents negative stock. No reservation or purchase order workflow yet.
- Notification queue atomic lease; configured optional customer email status updates (Resend) and existing owner WhatsApp/email/webhook. Email does not include secret access code. External providers require valid configuration; retries after process crashes can still duplicate provider delivery when provider lacks idempotency. WhatsApp preference is stored; automatic customer WhatsApp templates are not implemented.

## Verified results

`npm test`: 12 passed, 0 failed (includes end-to-end HTTP/API customer and staff workflow using isolated SQLite and mocked provider). `npm run audit`: 23 passed, 0 failed. Public and backend JavaScript syntax checked. The test QR is deliberately a tiny non-payment PNG in test fixtures only; no real QR or real charges in the app. See `TEST-RESULTS.txt` for actual logs. The installed Chromium has an administrator URL block policy; real browser E2E, responsive/visual checks and actual Windows launchers were not verified here. No real customer records or merchant credentials were supplied.

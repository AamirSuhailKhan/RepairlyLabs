# RepairlyLabs — browser-based owner and team access

## Apply the login update (Windows, no commands to type)
1. Close the old running RepairlyLabs server window (or stop the old server through your hosting control panel). Back up the existing project and its SQLite `data` folder, including any configured external DATA_DIR. Back up while the server is stopped.
2. Extract the **login fix patch**. Copy ALL files and folders from the patch into the EXISTING RepairlyLabs project root (the folder containing package.json). Choose Replace for the matching source files. Do not delete or replace your existing data directory or .env. The patch does not contain either.
3. Double-click `Recover Owner Account.vbs`. This uses your installed Node.js (22.13+) and the same project's .env / DATA_DIR. It starts the updated local server if required and opens a private one-time browser link. JavaScript in the webpage removes the link secret from the address bar. Windows may require you to allow locally downloaded scripts after reviewing their source. Do not disable operating system security controls.
4. In the browser, enter your preferred email address and a new unique password of 12–150 characters. Confirm it and select Save owner access. Your existing owner username remains valid (typically `owner`). An email address is an additional login identifier, not Google sign-in. Sign in with either the email alias or the original username and the new password.
5. For daily use, double-click `Start RepairlyLabs.vbs` or visit http://localhost:3001/admin while the server is running. The port follows .env. Your session lasts up to 7 days, unless you sign out or the session is revoked. Use Security in the dashboard to change your login email or password, create team accounts, reset team passwords and disable/enable team access.

No terminal commands are needed for normal local access or local owner recovery. A Node installation and a running local server are still needed. The launchers are Windows-only. `Start RepairlyLabs.vbs` starts a hidden server process if none is running. To shut down a hidden local server, use Windows Task Manager and identify the relevant Node process by its command line before ending it. Do not end unrelated Node applications. If you have another server listening on the configured port, stop it first; the launcher refuses to use an older server without the new access endpoint. If Windows Script Host is disabled by policy, ask the machine administrator to run the reviewed launcher under an approved method.

## Existing accounts and data
The update makes an additive schema migration. It does not delete bookings, orders, parts, repairs, quotations, payments or existing accounts. The old `owner` account becomes the owner if it exists; otherwise the first existing account by creation date/username is assigned owner. On a new empty database, private recovery creates an owner account. Other existing accounts remain team accounts, with the same broad operations permissions as before. This is not a full per-module role-based access control system.

The `.env` ADMIN_USERNAME and ADMIN_PASSWORD settings are only for the legacy command-line setup script, not browser login or recovery. Avoid running that script again after browser recovery; it can explicitly change a stored password. Remove old ADMIN_PASSWORD values from .env when no longer needed; don't publish that file. Browser passwords are stored as scrypt hashes in SQLite, not clear text. The email is an alias, not a verified email-recovery channel.

## Security and recovery
No public registration and no public unauthenticated token generation. A trusted local operator creates a random 256-bit recovery token in the database. The server stores only its SHA-256 hash. A token expires after 15 minutes, is single use, and generating a new token invalidates earlier tokens. Successful owner recovery revokes owner sessions. Team management requires an owner session, CSRF token and current owner password. Disabling/resetting a team account revokes its sessions. An account may use a unique email alias, with collision protection against existing usernames and aliases. The application does not send Gmail/SMTP recovery messages or offer Google OAuth.

## Hosted production deployment
Deploy the updated source using your normal hosting control panel with HTTPS and persistent SQLite storage. The local VBS launcher intentionally refuses NODE_ENV=production and cannot access a remote server's database. For a hosted owner who forgets the password, a trusted hosting operator with access to the same persistent database must issue a token via the exported `issueRecovery(db)` function and privately open `https://your-domain/admin#recover=TOKEN` (never transmit it publicly or put it in access logs). No email-based remote recovery is included. Team account changes and password updates work directly in the hosted browser after sign-in. Never expose the local launcher or database as web assets. Review hosting/access privileges and rotate previously exposed credentials.

Access tests cover first-owner setup, recovery reuse/expiry, alias login, legacy accounts, owner-only team management, wrong passwords, duplicate emails, disabling and revoking sessions, changing a password and preserving bookings. The browser localhost navigation was blocked by the test environment; full browser and actual Windows launcher execution remain to be verified on your Windows PC. Existing Razorpay and notification integrations remain unchanged and require their usual credentials and live verification.

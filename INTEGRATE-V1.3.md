# RepairlyLabs V1.3 — Extended operations integration

## Base and safe installation
This package is built against `RepairlyLabs-1.2-Report-Fixes.zip`. It contains the entire source tree and an additive SQLite schema. An optional delta archive contains the changed files relative to that exact V1.2 base. If your actual local code is newer or forked, have your coding agent merge changes rather than blindly replacing files. No live database, `.env`, merchant QR, credentials or owner password is included.

1. Agent: stop the actual application, identify its real DATA_DIR, and run the existing `npm run backup` against it. Save a separate copy of current source, `.env`, and backup. Check restoration in an isolated directory.
2. Merge or replace the code while preserving the actual data directory and `.env`. Do not run setup unnecessarily or create a new owner. The new tables are created on startup. Node 22.13+ is required; tested with 22.16.0.
3. Copy only relevant new variables listed in `.env.example` into existing configuration. Do not reset existing variables. For Docker use a recent Compose version supporting optional env_file; Dockerfile healthcheck now uses /api/ready. Keep persistent volume and configure HTTPS and PUBLIC_ORIGIN. Do not deploy the writable SQLite file on an ephemeral serverless filesystem.
4. Run `npm test` and `npm run audit` against the test fixtures, not production data. Run the browser test against its isolated database. Then restart the actual app and sign in at `/admin` using your existing credentials.
5. Admin → Extended operations (`/operations/?admin=1`). Use the repair/order reference to open job tools. The existing owner-only business QR settings and customer static QR verification are unchanged. Customer route: `/operations/` (OTP, history, PDF, gateway QR). Related portal links take the private capability via the URL fragment, then strip it from the URL. Do not share links containing the code.

## Configuration and providers
- **Your existing UPI QR:** no gateway needed. Only confirm claims after checking merchant bank credit. Never use a screenshot or UTR alone as proof. This code does not automatically verify a plain QR image even if it contains a valid UPI ID.
- **Gateway QR:** requires actual merchant activation and Razorpay QR entitlement, `RAZORPAY_KEY_ID`, `RAZORPAY_KEY_SECRET`, and `RL_GATEWAY_QR_ENABLED=1`. Keep existing webhook secret for standard checkout. Use test keys only until provider and security tests are completed. Fixed amount, single-use, 30-minute requested expiry; fetches provider QR payment collection and accepts only exact captured payment. Polls every 60s while server runs. Known QR open attempts are reconciled; a failed/uncertain create without stored provider identifier stays locked. Owner may link an independently found provider QR with matching notes/reference/amount. Do not submit repeated QR payment if capture is pending. Closed, zero-payment QR only releases after a grace period and provider verification; unusual states need owner review. Direct provider QR image host must match approved Razorpay domains; verify returned host in merchant test environment. No QR webhook integration in this version; periodic/API-poll reconciliation. Direct bank API for arbitrary uploaded QR is not included.
- **Gateway refunds:** use original captured gateway receipt and reason in Extended operations, owner only, before delivery. Confirmation initiates real refund with live keys; do not test with live keys. Uses durable refund attempt receipt and `X-Refund-Idempotency`. If response uncertain keep the same attempt/receipt; use refund-check, not a new request. Known provider IDs polled every minute. Only provider `processed` creates a ledger adjustment. Post-delivery refunds/credit notes, externally initiated refunds and unusual gateway disputes require separate reconciliation. Verify eligibility and refund receipt behavior with provider test account.
- **SMS OTP:** `TWILIO_ACCOUNT_SID`, `TWILIO_AUTH_TOKEN`, `TWILIO_VERIFY_SERVICE_SID`; configure India delivery, allowed destinations, compliance and cost controls with provider. Per-phone rate limits. Verified sessions expire after one hour, and permit account history for matching phone only. Access code fallback remains. Phone-number reassignment and shared phones remain business/privacy risks; verify customer identity before handling sensitive records.
- **Customer WhatsApp:** configure existing `RL_WA_TOKEN`, `RL_WA_PHONE_ID`, `RL_WA_GRAPH_VERSION`, plus `RL_WA_CUSTOMER_TEMPLATE` and `RL_WA_CUSTOMER_LANGUAGE`. Approved template BODY requires exactly two text parameters in order: event/status and reference. Only sends for opted-in repair customers; no marketing/no private access code. Existing outbox provides retries and status logs. Provider accepted is not proof of delivered/read. Parts-order customer updates and delivery receipt callbacks are not implemented. Verify actual template and consent workflow before enabling.
- **Authenticator 2FA:** agent generate a random 32-byte key (64 hex characters) locally, store it as `RL_MFA_KEY` in `.env` without printing it in chat/logs. Back up securely. This encryption key must remain stable. Admin → Extended operations → Authenticator security → Begin enrollment using current password, enter secret manually in a trusted authenticator app (time-based, 6 digits); enable using code. Re-login on next unused 30-second code. Disable requires password and unused current code. If authenticator/key lost, trusted hosting operator backs up database and runs `node scripts/agent-mfa-recovery.mjs --confirm-owner-mfa-reset`, then uses the existing trusted owner recovery flow if necessary. Public email password recovery does not bypass 2FA. No public MFA reset route. This operator recovery is a local maintenance action, not a daily workflow.

## Local modules
- PDF billing statement: real downloadable PDF; private access enforced, reference, service/part lines, total, receipts and refunds. Not a legal GST tax invoice. Built-in PDF font replaces unsupported non-Latin characters; complete Unicode/Devanagari remains visible in web records. For legal tax documents add jurisdiction-appropriate invoicing after consultation.
- Supplier and purchasing: supplier create/list; single-SKU purchase orders, receive/cancel; transaction-safe stock increments and weighted-average purchase cost. For existing stock the owner sets opening cost first. Does not provide a full supplier lifecycle, purchase returns, payable accounting or multi-line PO documents.
- Costs/expenses: historical SKU cost snapshots on repair stock consumption and parts confirmation; known-cost contribution, refunds, recorded operating expenses. Historic/unlinked costs and labour may be missing; no claim of audited net profit or tax accounting. Report lists latest 250 completed jobs/orders, expenses aggregate all-time. Manual expense void API is owner-only with password; no void UI in this version.
- Private intake photos: up to eight PNG/JPEG per repair, 500 KB each; accessible to owner, manager, assigned technician only. Do not photograph device passcodes/private content. Plan retention and backups; data is stored inside SQLite, not public assets. No camera capture or automated redaction.
- Pickup/delivery: manually tracked stage, driver, date, notes and events, valid transitions; verified existing repair delivery workflow must finish before logistics handover. No live GPS/dispatch integration or route optimization. Schedule and verify physical delivery independently.
- Appointments: manager sets capacity per day and Morning/Afternoon/Evening; enforced inside booking transaction if both date and slot provided. Unconfigured/unspecified slots remain requests, not confirmed reservations. Existing booking form shows availability and disables full slots; no automated calendar confirmation/rescheduling.
- Customer history: owner/manager lookup by phone, verified phone portal provides recent 100 repairs and 100 orders, links to existing authorized portals. No complete CRM customer profile or pagination beyond these limits.
- Hindi: new operations interface bilingual; key storefront navigation and booking labels translated. The rest of existing storefront, admin, error strings, data labels and notifications remain English. This is not exhaustive localization.
- Monitoring: owner health dashboard (DB quick check, queued notifications, payments, uptime/memory), /api/ready checks DB connectivity, Docker healthcheck, optional privacy-preserving HTTP status/timing logs `RL_REQUEST_LOG=1`, external probe script `node scripts/monitor-check.mjs https://your-domain` suitable for a host uptime monitor. Configure external alerting/retention in hosting dashboard. No external alert account is created.

## Testing
`npm test`: 17 test cases, including V1.2 regression suite and new integrated test. External APIs mocked; no real SMS, WhatsApp, charges/refunds performed. `npm run audit`: 23 checks. JS syntax checks passed. The supplied `tests/browser_e2e.py` starts its own isolated database; install Python Playwright and Chromium on a permitted machine (`pip install playwright`, then `python -m playwright install chromium`). Agent executes `python tests/browser_e2e.py`. It checks desktop/mobile admin login, operations form, language toggle and Repair Desk. In this environment navigation to localhost was blocked by browser administrator policy (ERR_BLOCKED_BY_ADMINISTRATOR). It was not possible to verify the browser flows. Do not label browser E2E passed. Browser suite is a starting smoke suite, not exhaustive.
